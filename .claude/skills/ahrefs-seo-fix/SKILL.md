# Ahrefs SEO 이슈 → PR

## 입력

`sa@ahrefs.com`이 보낸 크롤 이메일, 또는 그것을 정리한 감사 보고서. 입력이 없으면 사용자에게 붙여넣어 달라고 한 문장으로 요청한다.

Ahrefs API는 계정 플랜이 지원하지 않으므로 쓰지 않는다. `app.ahrefs.com` 딥링크는 로그인이 필요해 열 수 없으니 시도하지 않는다.

## 핵심 원칙

**이슈 개수가 아니라 원인 개수로 작업한다.** Ahrefs는 증상을 URL 단위로 센다. 같은 이슈가 46개 페이지에서 잡혀도 원인은 컴포넌트 한 곳일 수 있다. 46개를 하나씩 고치는 PR을 만들면 안 된다. 다만 이 묶음을 **가정하지 말고**, 실제 코드를 확인해 판단한다.

**고치기 전에 확인한다.** Ahrefs 보고와 실제 코드가 어긋나는 경우가 있다. 보고를 믿고 코드를 바꾸지 말고 항상 실제 파일을 먼저 읽는다. 어긋나면 그 사실 자체를 PR에 적는다 — 진짜 버그일 때가 많다.

**사람이 읽는 문구는 생성하지 않는다.** meta description, alt text, 제목을 지어내지 않는다. 페이지 본문에서 요약할 수 있으면 하고, 아니면 대상 목록만 뽑아 사용자에게 넘긴다. 검색 결과에 노출되는 문장을 AI가 지어내면 품질 문제로 돌아온다.

## 절차

### 1. 대응 여부 확인

각 이슈에 대해 **이미 대응 PR이 있는지** 먼저 본다.

```bash
gh pr list --state all --limit 50
```

브랜치명·제목·본문에서 그 이슈를 다루고 있는지 확인한다. 매칭되는 PR이 있으면 건너뛴다 — 열려 있으면 리뷰 대기, 머지됐으면 다음 크롤에서 검증된다. 없으면 대응 대상이다.

이것이 중복 작업을 막는 유일한 기준이다. 지난 크롤과 개수를 비교하지 않는다.

### 2. 시급도 분류

개수 순이 아니라 **유입 손실 위험 순**으로 정렬한다.

| 등급 | 기준 |
|---|---|
| P0 즉시 | 색인/접근이 깨짐 — 5XX, 내부 4XX, 의도치 않은 noindex, canonical 오류, redirect loop, robots 차단 |
| P1 이번 주 | 유입에 직접 영향 — orphan page, indexable page not in sitemap, slow page, 큰 이미지, title/meta description **누락** |
| P2 여유 될 때 | 품질 개선 — meta description too short, page has links to redirect, missing alt text, title too short |
| P3 순위 영향 없음 | OG tags incomplete, X (Twitter) card missing, external 3XX |

표에 없는 이슈가 나타나면 기준에 따라 직접 배정하고, **어떤 이슈를 어느 등급에 왜 배정했는지 보고에 남긴다.**

처리 대상은 **P0·P1 전부**와 **P2·P3 중 수정 1건으로 여러 개가 해결되는 것**이다.

### 3. 수정 범위 파악

**작업 트리가 깨끗한 상태에서** 수행한다. 테스트를 돌릴 때와 같다 — 아무것도 고치기 전에 전체 범위를 먼저 파악한다. 트리가 더러우면 사용자에게 먼저 알린다.

대응 대상 이슈마다 **subagent를 하나씩 띄워 병렬로** 조사시킨다. 각 subagent에게:

- 이 이슈가 레포의 어느 파일/설정에서 비롯되는지 찾을 것
- 수정이 필요한 파일 목록과 근거를 반환할 것
- **읽기만 하고 고치지 말 것**
- 다른 이슈와 원인을 공유하는 것으로 보이면 함께 보고할 것

레포마다 구조와 스택이 다르다. 어느 파일을 봐야 할지 미리 가정하지 말고 실제로 탐색한다.

결과가 모두 돌아오면 원인별로 병합한다. 이슈 10개가 원인 3개로 줄어드는 것이 정상이다.

### 4. 수정

**원인 하나당 브랜치 하나.** 여러 원인을 한 PR에 섞지 않는다 — 리뷰가 불가능해지고 하나가 잘못되면 전부 되돌려야 한다.

```
seo/<이슈-슬러그>-<YYYYMMDD>
```

예: `seo/og-tags-20260827`, `seo/trailing-slash-20260903`

빌드가 통과하는지 확인한다. sitemap이나 메타 태그처럼 빌드 산출물에 반영되는 변경은 `dist/` 결과물을 **실제로 열어** 확인한다. 소스만 보고 됐다고 하지 않는다.

판단이 서지 않는 것은 고치지 않는다. 특히 orphan page는 의도적으로 숨긴 페이지일 수 있으므로, 확신이 없으면 링크를 추가하지 말고 PR에 질문으로 남긴다.

### 5. PR

제목: `fix(ahrefs): <내용>`

```
## 원인
(한 줄)

## Ahrefs 이슈
- <이슈명>: <N> URLs (<등급>)
→ 다음 크롤에서 해소될 것으로 예상되는 범위

## 변경 사항
(파일별 한 줄)

## 확인 방법
(빌드 후 어디를 보면 되는지)

## 사람 검토 필요
@llqqssttyy
(판단이 필요한 항목. 없으면 이 섹션 생략)
```

사람의 판단이 필요하면 **반드시 `@llqqssttyy`를 멘션**한다. 문구를 지어내지 않고 남긴 목록, 의도 확인이 필요한 페이지, 코드와 Ahrefs 보고가 어긋난 지점이 여기 해당한다.

예상 해소 범위는 근거가 있을 때만 단정한다. 아니면 "일부 해소 예상"으로 쓴다.

## 하지 말 것

- 여러 원인을 한 PR에 묶기
- 코드를 확인하지 않은 채 보고만 보고 수정
- meta description, alt text, 제목 등 사람이 읽는 문구를 생성
- 의도적으로 숨긴 페이지에 링크를 추가
- 수정 범위 파악 전에 파일을 건드리기
- Ahrefs 딥링크를 열려고 시도 (로그인 필요)
- Ahrefs Always-on audit 같은 유료 업셀을 권유
- 다음 크롤 전에 "해결됐다"고 단정 — 검증은 다음 크롤에서 이루어진다
